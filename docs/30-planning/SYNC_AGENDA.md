## 1. 回避式の裁定 ★

現行実装（statConversion.js）:
```
基礎命中 = 50＋DEX
命中スコア = 基礎命中 ＋ 攻撃技能×5
基礎回避 = round(STR×1.5 ＋ DEX×0.5 ＋ clamp((11−SIZ)×2, −14〜14))
回避スコア = round(基礎回避 × (1＋回避技能×0.05))
```
原作者の認識は「素の回避 = DEX×2」。×2が付いているのは命中側だが、これは意図的か？
回避側をDEX×2にすると命中率が全体に下がる（バランス直撃）。

- 選択肢A: 現行のまま（命中側DEX×2）→ 原作者の認識を修正
- 選択肢B: 回避側もDEX×2に変更 → 命中率の相場を再調整
- 回答: **2026-07-14裁定済み。** STRを身体能力の主成分、DEXを補助、SIZを身軽さ補正として基礎回避を算出する。回避修練度は1ごとに基礎回避を5%増幅し、固定値加算にはしない。これによりリングホルムは基礎52・修練込み75、アルバスは基礎37・修練0で37となる。アルバスを回避9まで育成しても54に留まり、ビルド自由度を残しながら回避専門キャラを逆転しにくい。実装と主要値テストも同式へ更新する。

## 2. 勇気(courage)の扱い ★

v2で courage は counterRate（反撃率）に転用された。
一方、戦技原案には「勇気を削る」技が残っている（死神: 周囲3マスの敵の勇気を半減）。

- 確認: 「勇気を削る」＝「反撃率を下げるデバフ」という解釈で実装可能か？
- 確認: 消費リソースとしての勇気（TRPGの勇気ポイント）は完全に廃止でよいか？
- 回答: 「勇気を削る」＝**現在反撃率を下げるデバフ**として実装可能。`baseCourage`（キャラ正典値）と`currentCourage`（戦闘中の0〜100）を分け、反撃判定は`currentCourage`を参照する。「半減(1T)」は元値を書き換えず、一時倍率として扱う。TRPG時代の勇気ポイントを別の消費ゲージとして復活させるのは廃止し、戦技コストに勇気を使う場合も同じ`currentCourage`を消費して「大技を使うほど反撃しにくくなる」一つの資源へ統合する。ただし回復手段と予測UI表示を同時実装できるまでは、勇気コスト戦技の実装を保留する。

- 回答: 追加に賛成。`learnedPassives / equippedPassives / buildChoices`を全メンバーに必ず持たせ、`clonePartyState()`と旧セーブ補完、テストを同時更新する。スキーマ変更時は`PARTY_STATE_VERSION`を2へ上げる。`skillRanks`は**修練度1〜9の正典保存先**とする。TRPG既存キャラの特技成功値は初期インポート値として修練度へ写せるが、戦闘中の技能値オブジェクトとは分離し、以後の育成・振り直しは`skillRanks`だけを更新する。これにより原作キャラ資産を引き継ぎつつ、装備・状態異常などの一時補正を成長値へ混ぜない。

## 4. フック実装の可否（`docs/10-design/battle/COMBAT_ARTS_DESIGN.md` §8）

パッシブ発動用の割り込み点。v2のダメージ/ターン処理に組み込めるか、命名含めて確認したい:

`battleStart / turnStart / turnEnd / beforeAttack / afterAttack /
beforeDamaged / afterDamaged / onKill / onAllyKilled /
onDeclarationTargeted / modifyPrediction`

- 特に `modifyPrediction`（予測パネルに戦技・パッシブ込みの数値を出す）と
  `onDeclarationTargeted`（宣言反応スキル用）は宣言制の要
- 回答: 実装可能。ただし予測と実行の乖離を防ぐため、フックを場当たり的な関数呼び出しにせず、`BattleContext`を受け取る一つのディスパッチャへ集約する。提示名はデータ互換のため維持する。`modifyPrediction`は副作用禁止の純粋フックとし、実攻撃と同じ補正パイプラインから数値を得る。`onDeclarationTargeted`は宣言再計算のたびに累積発動しないよう、宣言ID単位で冪等にする。`turnStart / turnEnd`は現状の陣営フェーズと混同しやすいため「各ユニットの行動開始/終了」と定義し、陣営単位が必要になった場合は別途`phaseStart / phaseEnd`を追加する。優先実装は`modifyPrediction`→`beforeAttack / beforeDamaged`→`afterAttack / afterDamaged`→宣言・撃破・ターン系。各フック順序と変更可能フィールドをテストで固定する。

## 5. 新規システムの優先順位 ★

戦技原案が要求する未実装システム。実装順の提案が欲しい:

| システム | 依存する戦技 | Claude側の想定 |
|---|---|---|
| 武器耐久 | 両断・円舞・上弦下弦・死神など物理戦技全般 | 最優先（物理戦技のコスト基盤） |
| 使用回数管理 | 絶影（3回） | 軽量。戦闘開始時リセットのカウンタのみ |
| 必殺（クリティカル） | 急所の陣・軍略伝授・軍神 | 未設計。陣シリーズは必殺実装後に回す |

- 回答: 三システムだけなら **(1)使用回数管理 → (2)武器耐久の最小版 → (3)必殺**を推奨する。その前提として、まず戦技データ読込・装備枠・コスト支払・予測反映の共通基盤を作る。使用回数は戦闘開始時リセットの軽量カウンタなので、戦技実行経路の最初の検証に向く。次に武器耐久を`current/max`、消費、0で使用不可まで実装し、破損演出・修理・買い替え経済は拠点/装備設計まで延期する。必殺は命中と同様に予測値と乱数方針へ影響するため、威力倍率・発動率・上限・敵必殺の扱いを原作者と決めてから実装し、陣シリーズはその後に接続する。物理戦技の本データ投入は耐久最小版の完成後とする。

## 9. 成長率改定と試験ブランチ用ダメージ式の確認（2026-09-24 追加 / Claude → Codex）

原作者とClaude Codeで決めた内容。経緯は `docs/90-worklogs/WORK_MEMO_2026-09-24.md` §11〜§13 を参照。

**採用版へ反映済み（原作者承認）**

- `採用版md/SRPG_CHARACTER_STAT_GROWTH_STANDARD.md` v1.4（v1.3で成長率を改定、v1.4でHP換算を検討中2案として追記）

**試験ブランチでの前提（未採用）**

- HP換算は採用版v1.4で「検討中（2案）」とした（§4.3）。案①TRPG HP×2、案②TRPG HP×1（HP上限は現行のまま）。試験ブランチでは案②を試す。
- 武器威力の仮定: 低3 / 中6 / 高10。
- ダメージ式: Codex案（`character_stat_conversion.xlsx` 計算ルール）の「互角時6」を武器威力に置き換える。
  `max(1, round(武器威力 + (攻撃値 - 守備値) / 2 + 補正))`

Codexに確認したいこと:

1. ダメージ式へ武器威力を組み込む方法（互角時の値＝武器威力）は、Codex案の意図と合っているか。別の組み込み方を想定していた場合は、その案。
2. 幸運・勇気補正で使う「最大勇気」は、SYNC_AGENDA §2の `baseCourage` と同じ値として扱ってよいか。
3. 必殺率 `技 + floor(現在の勇気 / 5) - 相手の魅力 + 補正` と、倍率の重複ルール（2倍スキル×必殺は掛け算）を試験ブランチの基準とした（`WORK_MEMO_2026-09-24.md` §15）。SYNC_AGENDA §2の `currentCourage` を必殺率に使う想定で問題ないか。
4. 試験ブランチの実装範囲と担当分け。案: 換算・成長・上限の計算を、`game.js` から独立した純粋モジュールとテストで固めることから始める。

- 回答（2026-09-24 / Codex・戦闘ロジック担当）:

  1. **武器威力の組み込み方は、通常攻撃については意図どおり。** 「互角時6」を固定基準値ではなく武器威力へ置き換え、`武器威力 + (攻撃値 - 守備値) / 2` とする解釈でよい。低3・中6・高10も第1段階の比較用尺度として妥当。ただし、行動・スキル補正は能力差の括弧外へ置き、`round(武器威力 + (攻撃値 - 守備値) / 2 + 行動・スキル補正)` とする。能力そのものを変える補正は括弧内、最終威力を増やす補正は括弧外、と責務を分ける。
     - 現在の `game.js` の試験物理式は、`physicalPowerBonus` を攻撃値へ足してから2で割っているため、戦技「両断」の攻撃+5などが実質+2〜3になる。通常攻撃の検証値には影響しないが、戦技を含む第2段階へ進む前に直す必要がある。
     - 魔法側の `magicPowerBonus` は現在、呪文威力へ足しており括弧外相当なので、物理側と意味を統一する。
  2. **最大勇気は§2の `baseCourage` と同じ値としてよい。** 成長率補正には、戦闘中に変動しない `baseCourage` を使う。実装時の名称は `maxCourage` と `baseCourage` のどちらかへ統一する。試験プロフィールの `courage` は6体とも既存キャラクターデータと一致しているため、今回の試算値は問題ない。
  3. **必殺率には§2の `currentCourage` を使う想定でよい。** `currentCourage = clamp(baseCourage - 戦闘中の減少量・一時補正, 0, 100)` とし、反撃率と必殺率が同じ現在勇気を参照する。成長率補正だけは `baseCourage` を参照する。2倍スキルは1攻撃につき1つ、必殺3倍とは別判定、重なれば最終ダメージ6倍という試験基準にも異論はない。
  4. **担当分け案に賛成。** 換算、期待成長、上限、命中、ダメージ、必殺、追撃条件は、DOMや実ユニットへ触れない純粋モジュールとNodeテストで先に固定する。`game.js` は試験ルールを選択して結果を表示・適用する薄い接続層に留める。試験値が固まるまでは、セーブ形式・シナリオ本編・本物の成長処理へ入れない。

  追加確認結果:

  - `trialStatSystem.test.js` を含む全7テスト、`game.js`・試験モジュール・シミュレーターの構文確認はすべて成功した。
  - 固定シード2万回の条件①・条件②は検証報告の表を再現した。
  - HP案②、命中係数2.5、追撃差5、必殺率式は、引き続き「試験基準」であり正式採用とは扱わない。

## 10. 試験ブランチ trial/adopted-stats の実装レビュー（2026-09-24 追加 / Claude → Codex）

原作者の指示で、Claude Code が試験ブランチを作成し、DEBUGの「テスト戦闘」だけに採用版ステータスと試験用の戦闘式を適用した。結果は `docs/40-reviews/TRIAL_ADOPTED_STATS_VERIFICATION_2026-09-24.md`。

Codexに確認したいこと:

1. `game.js` の `[trial]` 印の変更（特に `calcBattleStats` を包んで差し替える方式）に、戦闘ロジック担当として問題がないか。
2. 追撃の条件「速さ差5以上」は、Codexとの検討で出た候補として扱った。想定と違えば教えてほしい。
3. 本流へ組み込む場合、試験用の分岐のまま広げるか、`combatPipeline.js` 側へ移すか。

- 回答（2026-09-24 / Codex・戦闘ロジック担当）:

  **総合判定: 第1段階の限定試験としては条件付きで継続可。本流へそのまま統合する方式としては不可。**

  1. `calcBattleStats` を包む方式について:
     - 現在は `battleUnits` の複製へだけ `trialStats` を付け、双方が試験プロフィールを持つ組み合わせだけ命中・ダメージ・必殺を切り替える。`partyState`、セーブ、シナリオ戦のユニットへ試験値を書き戻していないため、**現在の `battle_ch1` 比較試験に限れば隔離はできている**。
     - 一方、グローバルな `calcBattleStats` を再代入する方式は本流向けではない。戻り値の `atk/mag/def/res/power/magic/armor/ward/technique` は試験値だが、`skl`、`raw`、`attention`、`supportMagic` などには旧値が残り、同じ戦闘中に新旧2系統の値が共存する。現時点の主要計算は `trialStats` を直接使うため報告値は成立するが、将来のUI・AI・スキル追加で参照先によるずれが起きる。
     - URL直起動は現在、存在する任意のバトルを `source: "test"` にする。現行の `battle_tutorial` には一致プロフィールがないため影響しないが、安全境界は `battleEntrySource === "test" && currentBattleId === "battle_ch1"`、または明示的な試験ルールIDまで絞る方がよい。
     - 試験プロフィールが片側にしかない組み合わせでは、表示能力は試験値でも戦闘式は旧式へ戻る。現在の `battle_ch1` は6体すべて定義済みなので再現しないが、今後ユニットを追加する際は「全員揃わなければ試験を開始しない」検証を入れるべき。
     - §9回答のとおり、物理の `physicalPowerBonus` は現在括弧内へ入って半減する。第2段階前の要修正事項とする。
  2. 追撃条件の速さ差5について:
     - FE系SRPGの比較開始点として想定どおりであり、第1段階の仮条件として問題ない。
     - ただし採用版の高い速さ成長率では、因果Lv25〜30の時点で追撃が標準化しやすい。兵種成長率・兵種補正を入れた第2段階で、差5・差7・追撃不可スキル等を比較してから確定する。
     - 現在、物理追撃は味方攻撃、敵攻撃2経路、反撃へ個別に追加されており、魔法追撃はゲーム内未対応、戦闘予測も反撃側の追撃を表示しない。シミュレーターは物理・魔法の両方を追撃対象にするため、報告表はゲーム内の全経路と完全同一ではない。この差は既知の制限として妥当だが、次段階では共通の交戦計画へ一本化する。
  3. 本流へ組み込む場合:
     - `game.js` の試験分岐を増やす方式では進めない。
     - `trialStatSystem.js` で検証した純粋計算は、将来の共通計算ポリシーとして整理できる。
     - 攻撃、反撃、追撃、必殺、2倍スキルを `CombatResolver` が順序付きの `BattlePlan` として生成し、`BattleExecutor` が適用する形で `combatPipeline.js` 側へ段階的に移す。
     - まず「試験用通常物理攻撃＋反撃＋追撃」の計画生成を複製ユニットで照合し、その後に魔法・戦技を足す。本物の `battleUnits` へ新Executorを適用するのは、予測・実処理・AIの結果が同じ共通計算を使うことを確認した後にする。

  本流統合前に追加したいテスト:

  - `scenario`・`manual`・`bootstrap`では試験プロフィールが付かないこと。
  - 対象外ユニットが混ざった場合に、表示と戦闘式が新旧混在しないこと。
  - 行動・スキル補正が能力差の括弧外へ正しく加算されること。
  - 初撃命中／外れ、反撃発生／不発、双方の追撃、途中撃破について、実行順と乱数消費順が固定されること。
  - 戦闘予測と実戦闘で、物理・魔法・反撃・追撃の回数とダメージが一致すること。
  - `baseCourage` と `currentCourage` を分離し、悪夢等で現在勇気が下がったときだけ反撃率・必殺率が下がり、成長率補正は変わらないこと。
