# 自作SRPG 複数チャット協働ガイド

作成日: 2026-09-24  
状態: 運用ドラフト  
対象: CodexおよびChatGPT上で役割別の担当チャットを作る場合

## 1. このガイドの目的

自作SRPGでは、マップ、美術、ゲームシステム、シナリオ、Unity実装が互いに影響する。

役割別チャットを設ける目的は、それぞれの分野を深く考えることであり、担当ごとに別のゲームを作ることではない。このガイドでは、全担当が同じ作品を作るための共通資料、役割、決定手順、引き継ぎ方法を定める。

## 2. 基本原則

1. チャットの会話履歴を共有記憶として扱わない。
2. 重要な判断は、会話だけで終わらせず共有ファイルへ記録する。
3. 各担当は、担当外の重要仕様を勝手に正式決定しない。
4. 提案、試作、正式採用を明確に区別する。
5. 既存のゲームコード、正式資料、素材を無断で上書きしない。
6. 矛盾を見つけた場合は、都合よく解釈せず統括チャットへ報告する。
7. 正式採用にはユーザーの確認を必要とする。
8. 世界観、キャラクター、遊びやすさの三つを同時に見る。

## 3. 共有の仕組み

同じCodexプロジェクト「自作srpg 2」で作成したタスクは、同じファイルを読める。ただし、他のチャットで交わした会話は自動的には共有されない。

したがって、担当チャットの開始時に次の二点を必ず伝える。

- 共通資料を最初に読むこと。
- 自分の担当範囲と、決定してはいけない範囲。

ChatGPTの通常チャットなど、ローカルフォルダへアクセスできないチャットを使う場合は、必要な資料を添付または貼り付ける。

## 5. チーム構成

```text
ユーザー（原作者・最終決定者）
    │
    └── 全体統括・Unity実装チャット
          ├── マップ・画像生成担当チャット
          ├── ゲームシステム設計担当チャット
          └── シナリオ担当チャット
```

必要になった場合のみ、音楽・効果音、UI美術、テスト・バランス調整などの専門担当を追加する。

## 6. ユーザーの役割

ユーザーは原作者であり、最終決定者。

主に判断すること:

- どの案が好きか。
- キャラクターらしいか。
- 世界観に合うか。
- 遊んで気持ちよいか。
- シナリオ上の意味が正しいか。
- どの提案を正式採用するか。
- 仮素材を正式素材へ置き換えるか。
- 公開先と公開範囲。

ユーザーがUnityやプログラミングの専門家になる必要はない。技術的な選択肢は担当側が比較して説明し、作品上の判断をユーザーへ求める。

## 7. 全体統括・Unity実装チャット

### 役割

- プロジェクト全体の整合性を保つ。
- Unity試作と本実装を担当する。
- 各担当の提案を技術面から検証する。
- 担当間の矛盾を整理する。
- 正式採用された内容を共通資料へ反映する。
- 現行ブラウザ版を比較基準として管理する。
- Git、テスト、ビルド、バックアップを管理する。

### 決定してよいこと

- 実装内部の安全な構造。
- 命名、フォルダ、テストなど作品内容を変えない技術事項。
- 承認済み仕様を実現するための細部。

### ユーザー確認が必要なこと

- ゲームルールの変更。
- キャラクターやシナリオの解釈。
- UIの正式採用。
- 大規模な移行や削除。
- 他担当の提案を不採用にする判断。

## 8. マップ・画像生成担当チャット

### 担当範囲

- 戦闘マップの構図。
- マップ視点。
- タイルセット。
- 建物、地形、装飾。
- 背景画像。
- 高低差や前景の表現。
- Tilemap向け素材規格。
- キャラクターのマップ用ドット絵。
- 必要に応じた画像生成と素材案。
- 章や戦闘目的に合う視覚的な導線。

### 必ず連携する内容

- マップサイズ。
- 移動可能領域。
- 地形効果。
- 出撃地点、増援地点。
- 勝利・敗北条件に関係する地点。
- 会話、宝箱、扉などのイベント地点。
- マップ視点とUIの重なり。
- タイル寸法とPPU。

### 勝手に正式決定しないこと

- 命中、ダメージ、成長率などの戦闘ルール。
- キャラクターの性格や正史。
- 章の結末。
- 地形効果の数値。
- 新しいゲームシステムの正式採用。

### 成果物

- マップコンセプト。
- 俯瞰図またはラフ。
- タイルセット。
- レイヤー分け案。
- 地形一覧。
- Unity取込用の素材仕様。
- 使用目的、仮・正式、出典を記録した素材一覧。

## 9. ゲームシステム設計担当チャット

### 担当範囲

- 基礎能力と派生能力。
- 成長率、能力上限。
- 兵種とクラス。
- 武器、魔法、技能、戦技、パッシブ。
- 移動、射程、地形効果。
- 命中、回避、ダメージ、必殺、反撃。
- ターンまたは行動順。
- 敵AIと行動宣言。
- 勝利・敗北条件。
- 非殺傷、撤退、説得のゲーム上の扱い。
- 難易度とバランス。
- データ形式と自動テスト条件。

### 必ず連携する内容

- シナリオ上必要な戦闘結果。
- キャラクター固有能力の意味。
- マップ側で必要な地形と配置情報。
- UIで表示すべき予測情報。
- Unity側で実装可能かどうか。
- 現行ブラウザ版との挙動差。

### 勝手に正式決定しないこと

- シナリオの正史。
- キャラクターの人格や関係性。
- 見た目だけを理由にしたルール変更。
- 未確認の新能力や新設定。
- ユーザーが保留にした項目の採用。

### 成果物

- ルール案。
- 採用、保留、不採用の区別。
- 計算例。
- 境界値と例外。
- データ項目。
- テストケース。
- UIへ渡す情報。
- シナリオへ返す結果タグ。

## 10. シナリオ担当チャット

### 担当範囲

- 章構成。
- シーン構成。
- 会話。
- キャラクターの感情と関係。
- 戦闘前、戦闘中、戦闘後イベント。
- 分岐。
- 正史、異聞、救済などの扱い。
- 説得、見逃す、トドメなどの意味。
- 戦闘目的と物語上の理由。
- 戦闘結果による後続シーンの変化。
- 背景、立ち絵、BGM、SEの演出指示。

### 必ず連携する内容

- 戦闘で取得する結果タグ。
- 生存、撃破、撤退、説得などの条件。
- マップ上のイベント地点。
- 登場ユニットと増援。
- システムとして実現可能な分岐条件。
- シナリオ画面に必要なUI。

### 勝手に正式決定しないこと

- 戦闘計算式。
- 能力値や成長率。
- 実装都合だけを理由にしたキャラクター改変。
- ユーザー未確認の正史変更。
- マップ制作量を大きく増やす仕様。

### 成果物

- シーン一覧。
- 登場人物。
- 台詞。
- 演出指示。
- 条件分岐。
- 必要な戦闘結果タグ。
- 必要素材一覧。
- 未決定事項。

## 11. 担当間の境界表

| 項目 | 主担当 | 必ず相談する担当 |
|---|---|---|
| マップの見た目 | マップ | シナリオ、システム、統括 |
| 地形効果の数値 | システム | マップ、統括 |
| 戦闘目的 | シナリオ | システム、マップ |
| 勝利条件の実装 | システム・統括 | シナリオ |
| 出撃地点 | マップ | システム、シナリオ |
| 増援 | シナリオ | マップ、システム |
| キャラクター固有能力 | システム | シナリオ、ユーザー |
| 戦闘予測UI | 統括 | システム、マップ |
| キャラクター解釈 | シナリオ | ユーザー |
| UIテーマ | 統括 | マップ、シナリオ、ユーザー |
| 正式採用 | ユーザー | 全担当 |

## 12. 提案から正式採用までの流れ

```text
担当チャットが提案
    ↓
担当別メモへ「提案」として記録
    ↓
他担当への影響を確認
    ↓
統括チャットが比較案と論点を整理
    ↓
ユーザーが確認・選択
    ↓
「正式採用」と明記して共通資料を更新
    ↓
Unity実装・素材制作・テストへ進む
```

会話中に良い案が出ても、この手順を通るまでは確定仕様ではない。

## 13. 提案の状態

すべての案へ、できる限り次の状態を付ける。

- `アイデア`: 思いつき。未評価。
- `検討中`: 比較や確認を進めている。
- `試作対象`: 実際に触って評価する。
- `保留`: 今は決めない。
- `正式採用`: ユーザー確認済み。
- `不採用`: 今回は使わない。
- `廃止`: 過去に採用したが置き換えた。

## 16. 統括チャットへ戻す条件

次の場合は、担当だけで進めず統括チャットへ戻す。

- 複数担当へ影響する。
- 正式採用が必要。
- 現行ゲームコードを変更する。
- Unityプロジェクトの基盤を変更する。
- 大量の素材を生成する。
- 既存資料と矛盾する。
- キャラクター解釈に確信がない。
- 工数が大きく増える。
- 破壊的変更や削除が必要。
- 担当範囲を越えている。

## 17. ファイル編集時のルール

- 調査依頼ではコードを変更しない。
- 既存資料を置き換える前に内容を確認する。
- 仮案は新規ドラフトへ記録する。
- 正式資料への反映はユーザー確認後に行う。
- 画像生成物は仮、候補、正式を区別する。
- 元画像を上書きしない。
- Unityの`.meta`を削除・分離しない。
- 他担当が作業中のファイルへ無断で大規模変更を入れない。
- 実装変更にはテストまたは再現確認を付ける。

## 22. 定期同期で確認すること

- 各担当で新しく出た提案。
- ユーザー確認待ち。
- 担当間の矛盾。
- 必要素材。
- Unity実装の制約。
- 現行ブラウザ版との差。
- 正式資料へ反映すべき決定。
- 保留のままでよい項目。
- 次の縦切り試作で確認する項目。

## 23. 避ける運用

- 各チャットへ全権を与える。
- 会話履歴だけを正本にする。
- 同じ仕様を別担当が別々に確定する。
- 仮の数値を正式採用として扱う。
- 画像の見た目だけで戦闘ルールを変える。
- 実装の都合だけでシナリオを変える。
- 世界観の都合だけで操作性を犠牲にする。
- 毎回すべての資料を無差別に読み込ませる。
- 担当外の大量作業を黙って始める。

## 24. 現時点の推奨運用

1. このチャットを全体統括として残す。
2. マップ・画像生成担当チャットを作る。
3. ゲームシステム設計担当チャットを作る。
4. シナリオ担当チャットを作る。
5. 各チャットへ、本ガイド内の開始プロンプトを送る。
6. 各担当は、まず調査と提案を行う。
7. 実装や大量生成は、統括とユーザーの確認後に行う。
