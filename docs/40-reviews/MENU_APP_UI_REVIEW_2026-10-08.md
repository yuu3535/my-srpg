# 携帯端末メニュー（アプリホーム試作）のレビュー

日付: 2026-10-08 / 総合担当（Claude Code）
依頼: `docs/30-planning/HANDOFF_MENU_APP_UI_REVIEW_2026-10-08.md`（Codex メニューUI担当）
状態: レビューのみ。コード・素材・本編／Unity は変更していない。コミットもしていない（原作者の指示）。
対象: `アイコン素材/携帯端末メニュー画面素材/太陽盤_コマンド試作01/menu-apps-preview.html` とその参照先。太陽盤・コマンド・採用アイコンの意匠、仮背景・仮マップの絵柄は評価の外。

## 確かめ方

- ローカルの静的サーバー（http://localhost:8931、`.claude/launch.json` の srpg-static）で、アプリ内のブラウザで開いた。file:// ではない。
- 画面の大きさを 1400×900 と、スマホ横の 844×390 にして、要素の実寸・文字の実寸・読み込んだ素材（Resource Timing）・動いているアニメーション・requestAnimationFrame の回数を JavaScript で測った。
- 試作の検証スクリプト6本はすべて PASS（verify-menu-apps / menu-preview / menu-position / wheel / icons / beta）。
- **測っていないもの**: 実機（スマホ）のフレームレート・メモリ・発熱、Safari、iframe の中（太陽盤）へのキーボード操作、フォントのない別のPCでの見え方。

## 重要度順の指摘

### 高1 スマホ横で文字が読めない大きさになる（測定）

844×390 の画面で、端末フレームありのとき全体の縮小率は **0.716**。そのときの実寸:

| 部品 | CSS の値（844基準） | 実寸 |
|---|---|---|
| アプリ名（身支度など） | 11px | **7.9px** |
| 残金・名声値 | 10px | **7.2px** |
| 見出しの「携帯端末」 | 9px | **6.4px** |
| 説明チップ | 12px | 8.6px |
| アプリのタイル（押す所） | 約84×99 | 60×71px（押す大きさは足りている） |

- 押せる大きさは足りているが、文字は 10px を下回り、スマホでは読めない。残金・名声値は「ホームで見える」が目的なので、特に影響が大きい。
- 該当: `menu-apps-preview.css` 2・5・6・10・16行目。
- 案（技術）: 844基準で、アプリ名 14px・数値 13px・チップ 15px 以上（縮小後に約10〜11px）。タイルの中の行の高さ（`grid-template-rows:64px 14px 11px`）も合わせて広げる。アイコンの意匠は変えない。
- 原作者の判断が要る点: 文字を大きくすると、タイルの中の詰まり具合（見た目の密度）が変わる。

### 高2 画面の中に端末のフレームを描くと、横幅の約23%を使う（原作者の判断）

- フレームの内窓は元画像 1799 幅のうち 1391.5（77%）。スマホの画面いっぱいに出しても、メニューは 0.72〜0.77 倍に縮む。高1の原因の大半はこれ。
- 実機のスマホそのものが「携帯端末」なので、ゲームの中ではフレームを描かない（または細い縁だけにする）案がある。PC の大きい画面ではフレームあり、スマホでは無し、と分ける案もある。
- 意匠の判断なので原作者に選んでもらう。**背景制作の寸法に関わる**（下の「結論」）。

### 高3 最初の読み込みが約19MB（測定）。表示の大きさに対して素材が大きすぎる

測定（1400×900、キャッシュなし）: 44件、合わせて約22MB（うち運命予報の素材約2.9MBは同じ物の2回目でキャッシュ。実際に通信した量は約19MB）。

| 素材 | 元の大きさ | 画面での大きさ | 量 |
|---|---|---|---|
| アプリアイコン5つ | 1254×1254 | 46〜64px | 各1.1〜1.5MB、計6.1MB |
| 太陽盤の円盤・光（4枚） | 1254×1254 | 406〜781px | 計4.6MB |
| コマンドの炎（2種） | 1254×1254 | 81px | 計1.2MB |
| マップの仮画像 | 1536×1024 | 440×166 の切り抜き | 2.0MB |
| 運命予報（枠・星・シール） | 1024×1536 | **閉じていても最初に読む** | 2.9MB |
| β版シール | 1024×1536 の1枚 | 約33%の切り抜き（115px） | 0.5MB |

- 展開したときのメモリの目安（計算。測っていない）: 1254×1254 の RGBA は1枚約6.3MB。アイコン・円盤・炎だけで約60MB。スマホの WebGL／ブラウザでは落ちる原因になりうる。
- 案（技術・意匠は変えない）:
  1. 表示用の縮小版を書き出す（元の PNG は原本として残す）。アイコンは表示 64px の3倍の **192px**、炎は 256px、β版シールは切り抜いて 128px 程度、円盤・光は表示の2倍（最大 1600px 前後）。見た目の差はほぼない（高い密度の画面でも2〜3倍あるため）。
  2. 運命予報の iframe は、最初に開いたときに `src` を入れる（今は `hidden` でも読み込まれる）。
  3. マップの画像は、章・場所ごとに **880×332（枠 440×166 の2倍）** で作る決まりにして、切り抜きの計算（viewBox）をなくす。
- 変更する所: 素材の書き出し（新しいファイル）と、参照のパス・`?v=`。旧配置ページは参照を共有するので、同じ縮小版を使えば一緒に軽くなる。必要なテスト: verify-icons / verify-beta の素材の照合（ハッシュ）を、縮小版用に分ける。

### 中1 マップの画像が読めないときの表示がない（既知）

- 依頼文のとおり。アイコンには「素材未読込」があるが、マップは空の枠になる。章・場所の画像に差し替える前に、読めないときの表示（暗い下地と場所の名前）を入れておくとよい。

### 中2 説明チップを2つのスクリプトが書き換えている

- `menu-preview.js` の message 受け取り（59行目付近）と `menu-apps-preview.js` の message 受け取りが、どちらも `#menu-tip` に書く。アプリに指を乗せている間に太陽盤から知らせが来ると、いったん太陽盤の説明に書き換わり、後から登録した方がアプリの説明に戻している（測定: 最後はアプリの説明になる）。登録の順番に頼っているので、どちらかを直すと壊れやすい。
- 案（技術）: チップを書くのは1か所（例: `menu-apps-preview.js` の `drawTip`）にし、`menu-preview.js` からは「太陽盤の選択が変わった」ことだけを渡す。旧配置ページにも影響するので、旧ページ側は今の動きのままにする分け方が要る。

### 中3 状態の文が古いページのまま

- `menu-preview.js` の `status()` が「配置試作：コマンド選択・時間帯切り替え・マップ入口を…」と出す。新ホームではアプリの説明がない。プレイヤーには見えない（試作ページの外の文）ので低めだが、確認する人が迷う。

### 低（確認できて問題がなかった所）

- 何もしていないとき: requestAnimationFrame の連続呼び出しは **0回／3秒**（ページ・太陽盤とも）。動いている CSS アニメーションは9個（太陽盤の火の粉6・時間帯3）で、すべて transform と opacity だけ。重い描き直しはない（測定）。
- 「炎・時間帯の演出」を切ると、動いているアニメーションは **0** になる（測定）。画面が隠れたときに止める処理（visibilitychange）もある（コードで確認）。
- アプリを押す → ダイアログが開き、中へ移る。Esc で閉じると、押したアプリへ戻る（測定）。
- postMessage は受け取る側で送り元のウィンドウを確かめている（`event.source`）。file:// のために送る先は `'*'`。本番を HTTP で配るなら `event.origin` も確かめるとよい（低）。
- 座標が CSS とモデル（`menu-apps-model.js` の boxes）の2か所にあるが、verify-menu-apps.cjs が一致を確かめている（44行目）。今のままでよい。
- イベントの外し方（disposers・pagehide）はそろっている。

## 今後の接続（本編は Unity。提案だけ）

本編は Unity 版なので、この HTML は**見た目と動きの正本**として扱い、Unity の UI に作り直す前提がよい（iframe・APNG はそのまま持ち込めない）。

| つなぐもの | 境目の案 |
|---|---|
| セーブ | Unity 側に仕組みがある（2026-10-08。`docs/30-planning/FOUNDATION_GAPS_2026-10-08.md` §8）。コマンドの「セーブ」から `SaveMenu.Open(Save)` か、`SaveStore.List()`・`SaveSystem.SaveTo/LoadFrom` で画面を作り直す |
| 時間帯 | 探索の場面の時間帯（Unity の配置表・見え方の朝・昼・夕方・夜）から渡す。時刻の数字は出さない（方針どおり） |
| 残金・名声値 | まだ仕様がない。決まったらセーブの中身に足す（版を上げる） |
| アプリの解放（謎のアプリなど） | 解放済みの一覧をセーブの中身に持つ。メニューは「一覧にあれば出す」だけにする |
| マップの窓 | 章・場所の id → 画像（880×332）の表を1つ作る。読めないときは場所の名前だけ |
| 運命予報の本文 | 章ごとの文を表にして渡す（今の縦書きの重ね方は、Unity では1枚の画面として作り直す） |
| 素材 | Unity 用には、表示の2倍程度の大きさで書き出す（高3と同じ縮小版を使える）。炎の APNG はコマの並んだ1枚の絵にする |

## 原作者の判断が要るもの／技術だけで済むもの

- **原作者の判断**: 高2（ゲームの中で端末のフレームを描くか。スマホと PC で分けるか）、高1の文字を大きくしたときのタイルの見え方。
- **技術だけ**: 高3（縮小版の書き出し・運命予報をあとで読む・マップ画像の寸法の決まり）、中1、中2、中3。

## 結論: 携帯端末の背景制作へ進んでよいか

**進んでよい。ただし、先に高2（フレームを描くか）だけ決める。**

- 背景は、高1・高3・中1〜3の直しとは別に作れる（重なりは背景の上に乗るだけ）。
- ただし背景の**寸法と見える範囲**は高2で変わる。フレームを描くなら内窓 844×390 の範囲（端は枠に隠れる）、描かないなら画面全体。どちらでも使えるように、**1688×780（844×390 の2倍）で作り、上下左右の端の約5%には大事な物を置かない**、とすれば、あとで決めても作り直しが少ない。
- 文字の読みやすさのため、背景はアプリ列・チップ・マップの窓の後ろが暗く落ち着いた明るさになるようにする（文字を大きくしても、背景がうるさいと読めない）。色は `docs/10-design/ui/COLOR_HARMONY_DIRECTION_2026-10-02.md` に合わせる。
